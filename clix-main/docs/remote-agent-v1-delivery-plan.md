# clix 远程 Agent 首版交付方案

状态：方案草稿，尚未实现。本文约定首版的范围、实现顺序和验收方式，不代表现有功能已经支持远程运行。

## 目标

用户在 Windows 本地项目目录输入 `clix`，使用运行在 Linux 服务器上的 Agent 处理任务。服务器调用模型并管理对话；本地客户端提供终端界面、执行本地文件工具和命令、接收用户确认。项目文件不整份上传，但 Agent 读取的文件内容和命令输出会发送到服务器，并可能发送给模型供应商。

首次安装并配置服务器地址、客户端凭证后，日常使用方式为：

```powershell
cd D:\work\my-project
clix
```

模型 API Key 保存在服务器上。本地项目、构建工具和命令运行环境留在用户电脑上。这个版本不要求用户登录服务器后启动终端程序。

## 首版交付范围

- 一台 Linux 服务器和 Windows 本地客户端；支持多个用户分别登录，用户之间的会话和数据隔离。
- 默认的 ReAct 执行方式：服务器循环调用模型和工具，直到完成任务或用户取消。
- 客户端交互界面、流式输出、当前目录识别和项目根目录限制。
- 本地工具：`read_file`、`list_dir`、`glob_files`、`grep_code`、`write_file`、`edit_file` 和 `execute_command`。
- `auto` 与 `ask` 模式、人工确认、本地安全检查、取消和断线后的状态提示。
- 按用户隔离的会话创建和历史查看；断线恢复只恢复可确认的会话状态，不自动重放有副作用的工具。
- 服务端配置、客户端安装和登录说明，以及本地模拟服务端和模型的自动化测试。

首版不承诺远程支持 `/plan`、`/team`、MCP、浏览器、图片、Skill、RAG 索引、快照回滚、微信、后台任务和完整 `/resume`。这些功能需要分别确定运行位置、权限和恢复语义，后续版本再接入。现有本地运行模式保留；远程模式遇到未支持的命令或工具时，明确提示不支持，不能悄悄转到服务器执行。

## 两端职责

| 内容 | 服务器 | 本地客户端 |
|---|---|---|
| 对话与模型 | 运行 Agent、管理上下文并调用模型 | 输入用户请求、显示模型输出 |
| 工具 | 按本轮策略判断工具是否可用，发出请求并接收结果 | 校验参数、检查路径和命令、执行工具并返回结果 |
| 确认 | 执行现有自动审查逻辑，记录审查结果 | 显示人工确认，用户决定是否批准 |
| 会话 | 保存属于当前用户的会话、事件和必要的工具结果 | 保存连接配置，提供本地终端交互 |
| 取消 | 停止继续调用模型和发起新工具 | 尝试终止正在运行的本地命令，并报告结果 |

客户端启动时固定项目根目录，服务端只传项目内相对路径。客户端对真实路径、符号链接和路径穿越进行检查，不能信任服务器给出的路径；服务器文件系统路径不能被当成本地路径执行。所有文件修改和命令均以本地检查为准。

## 连接和消息

客户端通过 HTTPS 和 WebSocket（双向实时连接）与服务器通信。服务端先验证客户端凭证和用户身份，再建立会话；每个会话绑定用户、客户端连接和本地项目标识。公网部署由反向代理提供 TLS 加密，服务端只监听本机或内网。协议包含版本号，双方版本不兼容时拒绝连接并给出升级提示。

消息使用 JSON，至少包含协议版本、会话 ID、任务 ID、消息类型；工具请求还包含请求 ID、工具名和参数。主要消息如下：

| 消息 | 方向 | 作用 |
|---|---|---|
| `session.start` / `session.ready` | 双向 | 创建会话并确认当前连接 |
| `user.message` | 客户端 → 服务端 | 提交用户输入 |
| `message.delta` | 服务端 → 客户端 | 逐段显示回复 |
| `tool.request` / `tool.result` | 双向 | 请求并返回本地工具结果 |
| `approval.request` / `approval.result` | 双向 | 显示人工确认并返回选择 |
| `turn.cancel` | 客户端 → 服务端 | 请求取消当前任务 |
| `turn.completed` / `turn.failed` | 服务端 → 客户端 | 报告本轮结束和原因 |

工具请求和结果按请求 ID 对应；重复、过期或属于其他用户及会话的消息不得执行。结果继续作为不可信工具数据处理，沿用现有工具结果标记和大结果处理规则。

## 执行、确认与断线

- 保持现有检查顺序：本轮工具策略 → 人工确认相关检查 → 参数校验 → 路径和命令检查。被安全策略拒绝的操作不能由用户批准。
- `auto` 模式的命令自动审查在服务器使用当前供应商完成；审查失败或不可用时不放行，连续被拦截后的人工确认仍由本地界面处理。`ask` 模式按现有规则请求人工确认。本地始终执行自己的路径和命令检查。
- 三种执行方式最终应共用工具执行入口；首版只接默认 Agent。只读工具并行和结果顺序沿用现有规则，写文件、命令和未知工具按顺序执行。
- 每个有副作用的请求记录接收、执行和结果状态。连接中断后不启动新的本地工具；如果操作可能已经执行但结果未收到，标记为“状态不明”，由用户检查，不自动重试。
- 用户取消时，服务器停止发起新工作；客户端尝试停止当前命令，并将实际停止结果返回。已经完成的写入不自动回滚。
- 服务端重启或客户端掉线后，可以查看已保存事件；首版不承诺恢复中途的 Agent 运行。不能因为恢复失败而重复执行旧操作。

## 代码改造

1. 在现有工具调用入口抽出可替换的执行方式：本地模式继续调用本地工具，远程模式将允许执行的请求发送给客户端。保留 `executeTools()` 的统一顺序和策略结果统计，不为远程模式另写一套绕过策略的循环。
2. 新增服务端连接、用户认证、会话归属、消息编解码和请求状态管理；模型客户端与 Agent 保留在服务端。现有 Runtime API 的会话存储可作为参考，但它当前的事件回放接口不具备双向工具执行和人工确认能力。
3. 新增客户端入口，复用现有终端显示和本地工具，增加登录、项目根目录固定、连接管理、确认、取消和结果回传。
4. 把服务器端输出转换为结构化事件，由客户端的 `Renderer` 显示；不在后台线程直接向用户终端输出。
5. 为远程模式设置明确的工具白名单；只在客户端实际具备并允许时向模型提供对应工具。服务器不可将未支持工具转到自身执行。
6. 保持现有本地模式的配置和行为可用；旧名称配置与数据的迁移单独处理，不能在首次启动时静默覆盖。

## 部署与交付物

- 服务端：可执行程序、配置示例、systemd 服务示例、反向代理配置示例、启动与升级说明。模型 Key 和客户端凭证不能写入仓库。
- Windows 客户端：安装包或安装脚本，将 `clix` 加入 PATH；交付时说明是否包含 Java 运行环境，以及登录、注销和更新方法。
- 运维说明：用户与凭证创建、撤销、日志位置、会话数据存放及备份；日志不记录密钥。
- 配置和数据迁移说明：列明新旧目录和环境变量，旧数据保留；迁移前检查冲突，不覆盖目标文件。

## 实施顺序

1. 修复或记录会影响首版的现有 Windows 工具测试问题；确定旧配置迁移方式。
2. 搭建带认证的连接、版本协商与会话隔离，使用模拟客户端验证。
3. 打通服务端默认 Agent 的流式对话和本地只读工具。
4. 接入本地写入、命令执行、`auto` / `ask` 确认与审计。
5. 完成取消、断线、状态不明和会话事件查看。
6. 打包 Windows 客户端与 Linux 服务端，完成部署文档和联调。

## 验收标准

首版交付时，以下场景均须通过：

1. 在 Windows 本地项目目录输入 `clix`，登录或连接 Linux 服务端；未授权客户端无法创建会话。
2. 使用模拟模型发起读取和搜索，本地返回当前项目结果；路径穿越和指向项目外的符号链接被拒绝。
3. 修改文件与运行本地测试时，确认和安全策略按模式生效；确认拒绝或安全检查失败时没有副作用。
4. 客户端断线发生在命令执行前、执行中和执行后结果回传前时，界面准确提示状态；有副作用的操作不会因重连自动重复执行。
5. 取消任务后不再启动新的工具；正在运行的命令终止结果可见，已完成的修改保留。
6. 不同用户不能读取彼此的会话和工具结果；日志不包含明文凭证或模型 Key。
7. 非远程本地模式和首版未支持功能的处理符合原有行为或给出明确提示。

测试优先使用模拟模型和本地测试服务，不调用真实模型、不运行 Docker 或评测。真实服务器联调作为单独的交付验收步骤，在部署环境和凭证准备好后执行。
